# M1B groundwork: Vibepollo/PyroWave protocol spike

**Status (2026-09-25): source audit started; no Asteria implementation or Windows interoperability claim.** This is the next development task after deciding to use Moonlight's built-in statistics for the initial M1A comparison. PyroWave remains optional and outside the first preview.

## Sources and revision boundary

- The [experimental streaming overview](https://github.com/joemossjr16/pyrowave-streaming/blob/main/README.md) links the host, Moonlight Qt, common protocol, and PyroWave codec forks. Its September 24 handoff reports end-to-end host/SteamOS-client tests, not Asteria Windows tests.
- The PyroWave-enabled Vibepollo host currently lives at [joemossjr16/pyrollo](https://github.com/joemossjr16/pyrollo) (the older `pyrowave-vibepollo` URL redirects). This is distinct from [Nonary/Vibepollo](https://github.com/Nonary/Vibepollo); do not infer PyroWave support from the latter's ordinary builds. Inspect and pin a tested host commit before implementation.
- The client reference reviewed here is [Moonlight Qt fork commit `92a4d93`](https://github.com/joemossjr16/moonlight-qt-pyrowave/tree/92a4d936986b28cad70a443a67b22bd79a723661), including its nested common protocol code. The host source search resolved to [`86a462f`](https://github.com/joemossjr16/pyrollo/tree/86a462feddadb0dcbe166fc61c36053e5441bdbf); pin the PyroWave library revision and submodule SHAs as part of a runnable test manifest.
- The [upstream PyroWave bitstream](https://github.com/Themaister/pyrowave/blob/master/bitstream/bitstream.md) is a draft byte-oriented packet format. Its codec packets are distinct from the private Moonlight frame container and network transport.

## Proposed Asteria boundary

Keep PyroWave behind an explicit experimental preference. Check local Vulkan/PyroWave decoder initialization **before advertising** the format. Extend the smallest common-protocol capability/SDP/depacketizer surface required for this private extension, then select a separate decoder in `app/streaming/session.cpp` at the existing video backend boundary. Keep existing H.264/HEVC/AV1 decoder/render paths, pairing, audio, input, and default pacing intact. Reject malformed `PYRW` frames with bounded memory use and release codec/GPU resources on stop or reconnect. This is a proposal pending a source diff against Asteria's pinned common-protocol revision.

## Questions and next checks

1. **Negotiation:** diff both forks' protocol code against Asteria's exact submodule pin. Confirm capability-bit collisions, SDP ordering, 4:4:4 selection, and behavior with ordinary Apollo/Vibepollo builds and old clients.
2. **Transport:** trace host RTP packetization, frame-size/FEC limits, loss handling, decoder input ownership, and maximum safe `PYRW` packet count/length. Test malformed and partial containers without accepting unbounded allocations.
3. **Windows runtime:** build a small decode/present proof on Windows x64 and ARM64 with pinned PyroWave/Granite/Vulkan inputs. Inventory every shipped DLL and verify ARM64 PE types. Check GPU feature support and device/renderer interop before offering the codec.
4. **Color:** verify SDR matrix, range and 4:2:0/4:4:4 output using known patterns; keep HDR excluded until the host, protocol, decoder and renderer agree on transfer/primaries and metadata.
5. **Fallback:** prove unsupported host, missing Vulkan feature/DLL, disabled opt-in, failed decoder setup, reconnect, and mid-session encoder failure behavior. A codec cannot simply change in the middle of the negotiated stream; a new standard-codec session is the safe recovery candidate.
6. **Performance:** compare against AV1/H.264/HEVC on the same host/client/network with Moonlight's existing statistics and any precisely identified missing metric. Record bandwidth and packet loss as well as decode/render timing. Do not change frame pacing on speculation.

**Spike exit:** a pinned revision map, protocol diff, Windows x64/ARM64 dependency assessment, color/fallback contract, and a go/no-go decision for an isolated opt-in prototype. No broad performance or hardware support claim follows from source inspection alone.
